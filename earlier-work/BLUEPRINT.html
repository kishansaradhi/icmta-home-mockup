Indian Commerce & Management Teachers Association

ICMTA Website Build Plan

icmta.in — a clean public presence, a searchable member directory with contact details protected, and announcements. Sized for the association we actually have.

01What we are building

A small website with a real database behind it. Three jobs, in the order they matter:

Announcements — seminars, conferences, circulars. Posted by the Secretariat, visible on the home page.

Member directory — searchable by name, expertise, designation, state. The point is finding a resource person: a Professor of Finance in Karnataka, a Ph.D supervisor in Marketing, a Principal who can chair a session.

Protected contact details — phone and email are stored in full, and shown in full only to the member themselves and to an admin. Everyone else sees a masked form.

Member records move out of the web page and into a database. Today the whole directory sits in a 2 MB JavaScript file that every visitor downloads, contact details included.

02The pieces

Pages
Static HTML on Hostinger — the existing site, unchanged in look. Home, About, Events, Membership, Directory, Contact.
API
Node + Express, one small service. Decides who may see what. Nothing else talks to the database.
Database
SQLite — one file, 324 KB with all 343 members loaded. No server to run, no credentials in transit.
Admin
A password-protected section for the Secretariat: add and edit members, post announcements, export the list.
Photos
Ordinary image files in a folder, one per member, served by the web server.

Why it must be in the database: if the API sends the full phone number and the page hides it with JavaScript, it is not hidden. It arrives in the browser and anyone can read it from the network tab. The masked view never has the real value to begin with.

04The database

Nine tables. Built, loaded with all 343 records, and included in the package.

-- the directory
member            name, institution, designation, qualifications,
                  email, phone, membership status
institution       name, city, state, pincode
member_expertise  which subjects each member covers
designation       Professor, Dean, Principal, Research Scholar …
expertise         Finance, Marketing, HRM, Research Methodology …
state             the 36 states and union territories

-- the rest
announcement      notices, seminars, circulars
user_account      login for members and admins
payment           membership fees, when we start collecting

-- three views control all access
v_public          no contact columns at all
v_member          contact masked
v_full            owner and admin only

Location sits on the institution, not the person. That is what makes "find me someone in Karnataka" work — and it took the directory from 141 members findable by state to 285.

05Step by step

  1. Confirm the disk survives a restart

    Ask Hostinger, in these words: does my Node.js app get storage that survives a restart or redeploy?

    WhySQLite is a file on the app's disk. If the container can be replaced with a fresh one, the file goes with it. A clear yes, or move to a VPS — this decides everything downstream, so settle it first.

  2. Put the database file outside the web root

    Something like /home/user/icmta-data/icmta.db — never inside public_html.

    WhyA database inside the web root can be downloaded by anyone who guesses the URL. That is the entire member list, contact details included, in one file.

  3. Stand up the API

    One Node service. Every route reads through a view; nothing selects from member directly except the owner's own row and admin screens.

    open
GET  /api/members              v_public — list + search
GET  /api/filters              states, designations, expertise
GET  /api/announcements        public notices

signed in
GET  /api/members/:id          v_member — masked contact
GET  /api/me                   v_full — own record
PUT  /api/me                   edit own record only
POST /api/auth/login | logout

admin
GET/POST/PUT  /api/admin/members
GET/POST/PUT  /api/admin/announcements
GET           /api/admin/export

    Set PRAGMA foreign_keys = ON on every connection — SQLite has them off by default, and without it every relationship in the schema is decoration.

  4. Point the directory page at the API

    Replace the <script src="js/member-data.js"> tag with a fetch('/api/members'). The page keeps its current design; only where the data comes from changes.

    WhyThis is the moment the 2 MB download and the open contact details both stop. It is worth doing on its own, before anything else on this list is finished.

  5. Add login

    Email and password. Hash with bcrypt, never store the password itself. Session in an httpOnly, secure, sameSite cookie. Rate-limit the login route.

    • Members get an invitation email with a one-time link to set their password
    • Two or three admin accounts for the Secretariat, no shared login
    • The detail page checks the session server-side and redirects to the membership page if there is none

  6. Build the admin screens

    Minimum useful set, nothing more:

    • Add / edit / deactivate a member
    • Post an announcement
    • Export members to CSV
    • A list of records with missing details, so the gaps get filled over time

  7. Put announcements on the home page

    Latest five, pinned ones first. This is what brings people back between conferences, and the site has had nowhere to put it.

  8. Set up backups before launch, not after

    sqlite3 icmta.db "VACUUM INTO '/backups/icmta-$(date +%F).db'"

    Nightly, keep thirty days, and copy at least one off the server — Google Drive is fine.

    WhyNever back up by copying the live file. A plain cp while a write is in progress can produce a database that will not open. VACUUM INTO takes a consistent snapshot.

  9. Clean up the old data before going live

    • Delete js/member-data.js from the repository
    • Merge the duplicate — ICMT334 and ICMT335 are both Vikhyat Pandey at Prestige Institute, Gwalior
    • Fill the three records with no designation: ICMT069, ICMT090, ICMT098
    NoteThe repository is public, so those 106 emails and phone numbers stay in the commit history even after the file is deleted. Removing them properly means rewriting history — worth doing once, at cutover, rather than later.

  10. Point icmta.in at it and tell the group

    Then invite members in waves — the founders first, then fifty, then the rest. Each wave confirms their own details and sets their own password.

    WhyEveryone at once means every question arrives at once, and there is one Secretariat. Waves keep it answerable.

  11. Add payments only when the association is registered

    A gateway needs a registered society or trust, a PAN, and a bank account in the association's name. Until then the payment table records cheques and transfers by hand, which is enough for the first year.

    The one rule to keepWhen the gateway is wired in, put a unique constraint on the gateway's payment reference. Gateways retry; without it, a retry credits the same payment twice and nobody notices until the accounts do not balance.

06What we are deliberately not building

Learning management

Moodle exists and is free. Nothing about our teaching needs is unusual enough to justify writing one.

Document repository

Papers and books link out to publishers and DOIs. Storing them means versioning, licensing and preservation — a publisher's job, not ours.

Content management

Fifteen mostly-static pages. If the committee wants to edit copy, announcements already cover it.

Event ticketing

Wait until we have run one conference through the site's announcements and know what is actually needed.

All of these stay on the long-term list. None of them is worth building before the directory is in daily use and the membership is paying for itself.
